# 灵豆微信小店多租户智能网关 (LingDou WeChat Shop Gateway)

本文档归纳了近期关于微信小店网关架构重构的核心功能、多租户机制以及日常维护与商品同步指南。

---

## 1. 架构升级：无状态多租户路由 (Stateless Multi-Tenant)

过去的 `gateway.py` 是单店模型，所有的鉴权 API 和知识库 ID 都是写死在代码或配置文件里的。为了支持公司未来无限开店的业务扩展，网关已被重构为了**纯无状态路由器**。

**工作原理：**
现在所有与“特定店铺”相关的身份信息，完全由前端请求的 URL 路径按规范传递。

* **新版 Webhook 格式：** 
  `http(s)://<网关IP或域名>:8010/webhook/{business_id}/{app_id}`
* **参数说明：**
  * `business_id`：灵豆后台创建的**知识库 ID**（例如 `wechat_shop`）。
  * `app_id`：当前微信小店的真实 **AppID**（例如 `wxad76052896802106`）。

### 🔌 以后新增一家微信小店要怎么做？
你**不需要改任何一行代码**。
1. 在灵豆后台建好该店的知识库，拿到对应的 `business_id`。
2. 确保贵司获取临时 Token 的通用接口已经可以支持该店的 AppID。
3. 直接去**该店的微信官方后台**，把消息回调 URL 填成：
   `https://您的实际域名/webhook/该店知识库ID/该店真实AppID`

网关在收到请求的瞬间，就会自动扒下这两个参数，兵分两路：一路去获取微信 Token，一路向特定的灵豆知识库请求对话。天然实现 100% 数据隔离，绝不串台。

## 2. 功能升级：自动化售后 SOP 与工单预警

网关现在内置了强大的“意图预处理”与“情绪安抚”逻辑。

* **精细化售后分类：** 能够精确识别用户的诉求，区分是催促物流（Urge）、发错货（Wrong）、破损（Damage）还是七天无理由退款（Refund）。
* **自动化索要凭证：** 当识别到破损时，AI 会在转人工前，自动柔性回复：“真的非常抱歉...麻烦您后续准备好送拍【内外包装破损照片】”。极大地降低了人工客服的沟通成本。
* **工单级预警标签推送：**
  处理完毕后，网关会通过统一的 JSON `issue_tag` 给下游业务系统返回一条**完整、高度结构化且包含了真实历史诉求**的预警信息：
  ```
  【商户工单推送模拟】分类: [🚨破损/少件/瑕疵] | 用户ID: wx_test... | 订单: 123456 | 诉求原话: 我买的草莓烂了 | 提醒: 请商户及时核实处理。
  ```
  系统更是引入了**时序追溯机制**：即使用户是分两次发话（第一句发牢骚，第二句才提供订单号），系统依然能精准顺藤摸瓜找到前面那句真实抱怨，绝不遗漏。

## 3. 日常操作指南

### 🚀 启动网关服务
进入 `wechat_shop` 目录，执行：
```bash
# Windows 环境
.\start_gateway.bat

# Linux 环境
sh manage.sh restart
```
网关默认运行在 `0.0.0.0:8010`。

### 🔄 如何同步一家新店的商品数据进知识库？

目前的 `sync_service.py` 已经被重构为支持多租户独立状态。您完全不需要去改任何 `config.json` 配置文件了！

只需要在控制台执行一句话命令，带上对应店铺的两个关键参数即可：

```bash
python sync_service.py --app_id 【新店的APP_ID】 --business_id 【新店在灵豆的知识库ID】
```
例如：
```bash
python sync_service.py --app_id wxad76052896802106 --business_id wechat_shop_2
```

**防串台保障：**
系统现在会自动为每一家店单独生成并维护自己的同步记录表（例如生成 `synced_ids_wxad76052896802106.json`），您不用再担心多店共存时互相覆盖导致漏发的问题。
